# RESU

On **Home**, enter `126974` to reveal **Quiz** and **RESU** for the current app session. RESU uses local Windows OCR; it needs no OpenAI key and makes no API requests.

## Setup

1. Select the Full game process and stop the main bot. The Quiz solver may remain enabled and continues watching and answering while RESU runs.
2. Choose **Select target key** (default `TAB`) and set **Select target key interval** from 50 to 10,000 ms. This is the minimum time between target-key presses and defaults to 500 ms. Type your exact **Resurrection key** in the empty text field, such as `3`, `F5`, `SPACE`, `ENTER`, or a letter. Set **Resurrection key presses** and **Burst duration** to control the resurrection spam. The default sends 10 presses spread from the first press to the last over 1.0 second. A zero-second duration sends them as fast as the configured key hold permits. `F12` is reserved for stopping RESU and can interrupt a burst.
3. To advertise or repeat a chat line, enable **Periodic typed message**, enter up to 200 characters, and choose an interval from 1 to 86,400 seconds. After each interval RESU sends `Enter`, pastes/types the configured message, then sends `Enter` again. The sequence is directed to the selected game window in the background and waits while a trade is visible or another RESU action is busy.
4. Open **Calibrate trade overlay and text regions**. Steps 1–4 define the target name, invitation detection, chat, and game-message areas. Step 5 is the invitation OK click.
5. Open the full trade window shown after accepting an invitation, then capture/calibrate again. Drag **overlay 6** around the entire full trade window, including its Trade buttons, character names, item slots, Rupiah labels, and Cancel. Set **overlay 7** on the Trade confirmation button inside overlay 6. **Show trade click overlay** displays point 5, the dashed overlay 6 detection rectangle, and point 7.
6. Use **Read OCR once** and adjust the message patterns to the actual server's wording. The default invitation detector recognizes `Request trade with Mojojo?` and extracts `Mojojo` as the user. The trade-dialog crop is enlarged three times before OCR so the game's small message font can be read. Each player-specific pattern requires a named `user` group. Payment additionally requires an `amount` group. Usernames must consist of 1–32 letters, numbers, underscores, or hyphens.
7. Set the minimum payment, payment deadline, and scan interval, then save settings. Start RESU. The selected game may stay behind other windows while RESU runs, but it must remain restored at the calibrated client size. Press `F12` or **Stop RESU** to stop.

Patterns are regular expressions applied separately to each OCR line. `^` and `$` anchor a match to the whole line. For example, `^(?<user>[\p{L}\p{N}_-]+) paid (?<amount>[0-9,]+) rupiahs\.?$` matches `Alice paid 1,000 rupiahs.` and extracts the payer and amount. Preserve any server-message prefixes in your actual patterns so ordinary player conversation does not match them.

## Behavior

- RESU selects a target, reads the target with the dedicated name OCR, requires two identical name reads, and checks the persistent, case-insensitive blacklist before casting. A temporary blank target read keeps the current selection; only four consecutive unreadable scans select another target. Nameplate level text and surrounding OCR punctuation are removed without guessing between ambiguous names. It re-reads the name immediately before starting the resurrection-key burst, then checks the selected window, restored/calibrated-size state, main-bot state, stop key, and blacklist before every press. Target and resurrection keys are posted directly to the selected game window, so another application may remain in the foreground. The most recently attempted player has a 30-second recast cooldown; paying customers remain eligible afterward.
- A new resurrection-confirmation message naming that player must appear in the message rectangle on two consecutive scans. An unconfirmed cast expires after 15 seconds of observed time without adding a blacklist entry.
- RESU accepts every recognized invitation or open trade window, regardless of the displayed username or whether a resurrection transaction is pending. The actual open trade layout is recognized from its `Trade` title/buttons together with `Rupiah` or `Cancel`; `OK` and OCR-misread `0K` remain fallback signals. While the calibrated trade region remains visible, RESU posts the calibrated trade-confirm click on a fixed 500 ms scan cadence (two attempts per second). Payment and blacklist tracking still use the exact resurrected character. Background clicks do not move the real cursor or take foreground focus.
- Trade completion/cancellation in the message rectangle stops acceptance. Closing a trade does **not** prove payment. A new payment message in chat or the message rectangle must identify the same player and meet the minimum amount. Two consecutive reads are required; existing visible chat history cannot settle the transaction.
- Following a confirmed resurrection, an explicit new nonpayment message or expiration of the monitored payment deadline adds the customer to the blacklist. Entries include a reason and timestamp and can be removed from the RESU tab. The timeout classifies an unconfirmed payment as unpaid; missed OCR can therefore require manually removing a name.
- Long OCR gaps and unreadable blank chat/message regions do not consume the payment deadline. Changing the selected process or starting another bot stops RESU. Minimizing the game or changing its client size pauses input until it is restored at the calibrated size or RESU is stopped and recalibrated.
- Add one or several exact character names by hand in the blacklist section, separated by lines, commas, or semicolons. Manual and automatic entries are saved in the app's existing settings file and are skipped before resurrection. RESU never starts automatically. Stopping discards the pending transaction without blacklisting it.

## Validation

Run `dotnet run --project tests/ResuService.Tests/ResuService.Tests.vbproj` for offline decision tests. These tests send no input and cover player identity, stale messages, payment amounts, deadlines, blacklist behavior, trade repetition/closure, and settings serialization. Actual server wording, OCR accuracy, and in-game input still require calibration and an in-game check.
